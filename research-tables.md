# Research: PDF table extraction for fact extraction

## Summary
For auditable fact extraction, the best default is not a single parser: use a high-provenance engine for OCR/layout (AWS Textract, Azure Document Intelligence, Google Document AI, or Adobe PDF Extract) plus deterministic validation against source coordinates and rendered table images. For local/open-source workflows, use pdfplumber/Camelot for simple digital PDFs, Docling or MinerU for scanned/complex RAG conversion, and Table Transformer/PubTables-style models when you need trainable table detection/structure recognition rather than a complete OCR-to-CSV product.

## Findings
1. **Digital vs scanned PDFs split the field.** Camelot’s classic parsers are for text-based PDFs, with Stream/Lattice/Network/Hybrid modes and explicit note that classic Camelot does not work on scanned PDFs; pdfplumber also says it works best on machine-generated PDFs. Cloud APIs, Docling, Marker, MinerU, and Table Transformer operate on rendered pages/OCR and therefore can handle scans, subject to OCR quality. [Camelot](https://camelot-py.readthedocs.io/en/stable/) [Camelot internals](https://camelot-py.readthedocs.io/en/latest/user/how-it-works.html) [pdfplumber](https://github.com/jsvine/pdfplumber/blob/stable/README.md)
2. **Simple digital tables: prefer deterministic tools first.** Camelot Lattice is strong for ruled/grid tables; Stream/Network are useful for whitespace/borderless tables and expose parsing metrics (`accuracy`, `whitespace`) plus CSV/JSON/Excel/HTML/Markdown/SQLite export. pdfplumber gives lower-level control over chars, lines, rectangles, bboxes, and table settings, making it better when you need custom extraction rules or visual debugging. [Camelot](https://camelot-py.readthedocs.io/en/stable/) [pdfplumber](https://github.com/jsvine/pdfplumber/blob/stable/README.md)
3. **Complex tables with merged cells/multi-row headers need structural models or cloud APIs.** Adobe PDF Extract reports table cells, formatting, row/column spans, CSV/XLSX/PNG renditions, and JSON table-cell attributes including `RowIndex`, `ColIndex`, `RowSpan`, `ColSpan`, `BBox`, `TH`, `TD`, and `TR`. AWS Textract explicitly extracts cells, merged cells, column headers, titles, footers, section titles, summary cells, and structured/semi-structured table type. Azure layout tables expose row/column spans, row/column header kinds, stub-head/description cells, spans, and bounding regions. [Adobe overview](https://developer.adobe.com/document-services/docs/overview/pdf-extract-api/) [Adobe schema](https://developer.adobe.com/document-services/docs/extractJSONOutputSchema2.json) [AWS tables](https://docs.aws.amazon.com/textract/latest/dg/how-it-works-tables.html) [Azure response](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/concept/analyze-document-response?view=doc-intel-4.0.0)
4. **Google Document AI has two different table stories.** The older Form Parser table extraction only recognizes conventional tables and states row/column spans are always `1`; the newer Gemini Layout Parser is aimed at complex PDFs/RAG and is documented as handling financial-report tables with merged cells and intricate headers, but with tighter online/batch limits. [Google handle response](https://cloud.google.com/document-ai/docs/handle-response) [Google Layout Parser](https://cloud.google.com/document-ai/docs/layout-parse-chunk)
5. **Table Transformer/PubTables-1M is a model component, not an end-to-end extractor.** TATR detects tables and recognizes table structure from images; its repository notes that text extraction from OCR or PDF must be supplied separately for HTML/CSV output. PubTables-1M provides 947,642 fully annotated tables with rows, columns, cells including blank cells, headers, bounding boxes, and canonicalized spans; reported TATR-v1.0 structure metrics on PubTables-1M include AP 0.902 and GriTS Top/Con/Loc around 0.985/0.985/0.979. [TATR GitHub](https://github.com/microsoft/table-transformer) [PubTables-1M paper](https://ar5iv.labs.arxiv.org/html/2110.00061) [HF Table Transformer](https://huggingface.co/docs/transformers/model_doc/table-transformer)
6. **Docling is the strongest local, auditable general-purpose choice.** Docling uses layout detection plus TableFormer for table structure; its docs say TableFormer recognizes rows, columns, cells, relationships, merged cells, and headers. DoclingDocument preserves layout/provenance (`page_no`, `bbox`, `charspan`) and exports Markdown, HTML, dictionary/lossless JSON, and DocTags. Its technical report emphasizes local execution, OCR for scanned inputs, TableFormer handling partial/no borders, spans, hierarchy, and avoiding generative hallucination. [Docling README](https://github.com/docling-project/docling/blob/main/README.md) [DoclingDocument](https://docling-project-docling.mintlify.app/concepts/docling-document) [Table options](https://docling-project-docling.mintlify.app/api/options/table-structure-options) [Technical report](https://arxiv.org/abs/2408.09869)
7. **MinerU and Marker are strong LLM/RAG converters, but less ideal as first-choice audit engines.** MinerU uses multi-module parsing with layout, OCR, formula recognition, and table recognition (TableMaster/StructEqTable), outputs Markdown/JSON, and table bodies as HTML with block bboxes/scores in structured files. Marker converts PDFs/images/Office to Markdown/JSON/HTML/chunks, supports OCR and LLM boosting, and its JSON table output includes `Table`/`TableCell` blocks with bboxes. However, both commonly optimize readable conversion; documented confidence and cell-level provenance are weaker than AWS/Azure/Google/Adobe/Docling. [MinerU paper](https://arxiv.org/pdf/2409.18839) [MinerU output docs](https://opendatalab.github.io/MinerU/reference/output_files/) [Marker README](https://github.com/datalab-to/marker?tab=readme-ov-file) [Datalab table JSON](https://documentation.datalab.to/docs/recipes/table-recognition/table-rec-api-overview)
8. **Confidence scoring is uneven and should drive vendor choice.** AWS exposes `Confidence` on `TABLE`, `CELL`, `MERGED_CELL`, `WORD`, etc. and defines confidence as recognition/geometry confidence. Google Layout objects expose `[0,1]` confidence and bounding polygons. Azure exposes word/selection/document-field confidence, but its `DocumentTableCell` class has no cell confidence field. Adobe Extract JSON schema has detailed table geometry/spans and char bounds but no confidence field. Open-source tools generally expose parsing heuristics or model scores, not calibrated per-cell confidence. [AWS Block](https://docs.aws.amazon.com/textract/latest/dg/API_Block.html) [Google Document](https://cloud.google.com/document-ai/docs/reference/rest/v1/Document) [Azure cell](https://learn.microsoft.com/en-us/python/api/azure-ai-documentintelligence/azure.ai.documentintelligence.models.documenttablecell?view=azure-python) [Adobe schema](https://developer.adobe.com/document-services/docs/extractJSONOutputSchema2.json)
9. **Reliability is domain-dependent.** A DocLayNet comparative study found TATR led table detection in Financial, Patent, Law & Regulations, and Scientific categories, Camelot led Government Tenders, and PyMuPDF led Manuals—evidence that document class matters. The same paper evaluated mostly digital-born PDFs, so scanned/OCR conclusions require separate testing. [Comparative study](https://arxiv.org/html/2410.09871)

## Decision guidance
1. **Strict fact extraction with audit trail:** Start with AWS Textract if you need per-cell confidence and explicit merged-cell relationships. Use Azure or Adobe when you need richer document/Markdown outputs or easier spreadsheet/table renditions; use Google Gemini Layout Parser for complex RAG-oriented financial/scientific reports.
2. **Private/on-prem pipeline:** Use Docling first. Add pdfplumber for deterministic validation on digital PDFs and TATR/FinTabNet or custom TableFormer/TATR training for recurring hard table classes.
3. **Simple digital PDFs at scale:** Try Camelot and pdfplumber before cloud APIs. They are cheap, fast, deterministic, and easier to debug, but require fallbacks for scans and irregular layouts.
4. **Complex financial/scientific tables:** Use AWS/Azure/Adobe/Google Layout Parser or Docling; compare against TATR models trained on PubTables-1M/FinTabNet when table structure is central.
5. **RAG ingestion rather than numeric fact extraction:** Marker, Docling, MinerU, Adobe Markdown, Google Layout Parser chunks, and Azure Markdown are all relevant. For facts, keep source coordinates/renditions and re-check numeric values against cell provenance.
6. **Recommended production architecture:** classify page as digital/scanned → run primary extractor → normalize table model (`page`, `table_id`, `row`, `col`, `rowspan`, `colspan`, `text`, `bbox`, `confidence`, `source_image`) → validate totals/headers/units → render source snippets for human review of low-confidence or high-impact facts.

## Gaps
- No single public benchmark compares all listed tools on the same scanned/digital, simple/complex, financial/scientific corpus with cell-level accuracy, confidence calibration, and provenance quality.
- Adobe, Marker, MinerU, Camelot, pdfplumber, Docling, and TATR do not provide uniformly calibrated per-cell confidence comparable to AWS Textract.
- Multi-page table stitching remains a post-processing problem for most APIs; even strong engines can split tables across pages.
- Next step: build a 50–100 PDF evaluation set from your target corpus, score exact cell text, header hierarchy, row/column spans, bbox IoU, numeric fact accuracy, and confidence calibration; then choose primary + fallback per document class.
