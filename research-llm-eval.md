# Research: LLM-based structured extraction from PDFs and evaluation methodology

## Summary
Use LLMs for PDF extraction when layouts, wording, and target schemas vary enough that rules or template-specific models become brittle, especially for semantic fields, clause interpretation, and cross-page reasoning. For production, prefer a hybrid pipeline: deterministic/OCR/layout/table extraction first, then schema-scoped LLM extraction with strict validation, per-field evidence, and regression metrics that measure not only valid JSON but grounded value correctness.

## Findings
1. **LLMs are best used selectively, not as a blanket replacement for rules/OCR/table models.** Use rules, regex, deterministic parsers, or specialized document AI models for fixed templates, stable identifiers, simple totals/dates, high-volume low-latency paths, and table/cell structure; use LLMs where fields are semantic, layouts vary, or business logic requires interpretation. AWS’s IDP guidance explicitly warns not to ask models to do rule-based operations over large data sets and recommends extracting structure at ingestion for “all the documents” queries. [AWS Generative AI Atlas](https://awslabs.github.io/generative-ai-atlas/topics/3_0_architecture_and_design_patterns/3_1_system_and_application_design_patterns_for_genai/3_1_2_architecture_patterns_by_application_type/3_1_2_2_intelligent_document_processing/3_1_2_2_2_information_extraction/information_extraction.html)
2. **Extraction quality depends heavily on the PDF representation.** Native PDF/image VLM input preserves visual cues, tables, diagrams, and scans but is costlier and constrained by page/context limits; parsed Markdown/HTML/JSON is cheaper, searchable, and easier to ground, but can lose reading order, table structure, or visual context. Gemini says PDF document understanding goes beyond text extraction to images, diagrams, charts, tables, and structured outputs up to 1000 pages; Claude converts each PDF page to an image and provides extracted text alongside page images; OpenAI’s PDF input guide says vision-capable models receive both extracted text and page images. [Gemini docs](https://ai.google.dev/gemini-api/docs/document-processing), [Claude PDF support](https://platform.claude.com/docs/en/build-with-claude/pdf-support), [OpenAI PDF/file inputs](https://developers.openai.com/api/docs/guides/pdf-files/)
3. **Do not assume OCR+LLM always beats image-only VLMs.** A 2026 EACL industry benchmark on business-document IE found image-only input can achieve performance comparable to OCR-enhanced approaches for powerful MLLMs, while schema, exemplars, and instructions materially improve extraction. Treat “direct PDF/page image vs OCR/Markdown” as an empirical routing decision by document class. [OCR or Not?](https://aclanthology.org/2026.eacl-industry.28/)
4. **Use layout-aware parsers as production infrastructure, not just preprocessing.** Tools/benchmarks such as Docling, olmOCR, and opendataloader-style PDF-to-Markdown evaluation measure reading order, tables, headings, math, and unit-testable page facts; their outputs can supply Markdown for prompts plus JSON/bounding boxes for evidence. olmOCR-bench uses 1,403 PDFs and 7,010 machine-checkable tests rather than soft edit distance alone. [olmOCR-bench](https://huggingface.co/datasets/allenai/olmOCR-bench/blob/main/README.md), [Docling](https://github.com/docling-project/docling), [opendataloader-bench](https://github.com/opendataloader-project/opendataloader-bench/blob/main/README.md)
5. **Schema-constrained outputs improve parseability but do not prove correctness.** OpenAI, Anthropic, and Gemini all support JSON Schema-style structured outputs, but they support subsets of JSON Schema, add latency/complexity, and still require semantic validation. OpenAI notes JSON mode only guarantees valid JSON while Structured Outputs enforce supported schemas; Gemini explicitly warns that syntactically correct JSON may still be semantically wrong; Claude documents grammar compilation, cache effects, schema complexity limits, and cases where refusals/token limits break schema. [OpenAI structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs), [Gemini structured outputs](https://ai.google.dev/gemini-api/docs/structured-output), [Claude structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)
6. **Large schemas are a known failure mode.** ExtractBench evaluates 35 PDF-to-JSON tasks across 5 schemas/4 domains with 12,867 evaluatable fields and found frontier models unreliable on enterprise schemas: aggregate valid JSON was 51%, aggregate pass rate 4.6%, and all tested models produced 0% valid output on a 369-field SEC schema. Structured-output mode did not solve this; overall validity dropped from 51% to 37% in their experiment due to schema rejection and complexity. [ExtractBench paper](https://arxiv.org/html/2602.12247), [ExtractBench repo](https://github.com/ContextualAI/extract-bench)
7. **Decompose complex extraction.** For large PDFs/schemas, split by document section, page range, table, or schema group; run smaller LLM calls with targeted context and merge/validate deterministically. ExtractBench’s analysis found output volume and schema breadth, not just page count or nesting depth, were dominant predictors of failure, so one giant prompt/schema is risky. [ExtractBench](https://arxiv.org/html/2602.12247)
8. **Ground every extracted value in evidence.** Require each non-null field to include a quote/source span plus page and preferably bounding box; then verify that the value is entailed by the evidence and that nulls are allowed only when evidence is absent. LangExtract maps extractions to exact source-text locations for traceability, while evidence-backed PDF extraction projects such as Pullcite emphasize quote + page + bounding box proof. [LangExtract](https://github.com/google/langextract), [Pullcite](https://github.com/usercando/pullcite)
9. **Evaluate hallucinations separately from omissions.** ExtractBench’s evaluator distinguishes present/null/missing states: gold present + predicted missing is omission; gold null + predicted value is hallucination. This distinction matters because omissions lose data while hallucinations inject false data into downstream systems. [ExtractBench methodology](https://arxiv.org/html/2602.12247)
10. **Use per-field metrics, not one global exact match.** Recommended comparisons: exact match for IDs/enums/codes; case-insensitive/fuzzy for names; normalized date match; numeric tolerance for money/quantities/percentages; semantic/LLM-judge match for descriptive text; precision/recall/F1 for arrays and repeated entities. ExtractBench implements schema-declared metrics including exact, fuzzy, semantic, numeric tolerance, and LLM array alignment. [ExtractBench repo](https://github.com/ContextualAI/extract-bench)
11. **Measure structure, value correctness, and source faithfulness independently.** The Structured Output Benchmark found JSON pass rates can be high while values are wrong: best value accuracy was 83.0% on text, 67.2% on image-derived OCR, and 23.7% on audio, with hallucinations inside JSON fields harder to notice because outputs look structurally valid. LLMStructBench likewise separates syntactic/document validity from semantic value errors, missing keys, missing values, and wrong values. [SOB paper](https://arxiv.org/html/2604.25359), [LLMStructBench](https://arxiv.org/html/2602.14743)
12. **Tables need table-specific evaluation.** For extracted tables, score table detection, row/column/cell structure, merged cells, cell text, and linkage from row/column headers to values. Use cell-level precision/recall/F1 or accuracy plus structure metrics such as TEDS and GriTS; PubTables-1M and GriTS show why table topology/content/location should be evaluated separately. [PubTables-1M](https://ar5iv.labs.arxiv.org/html/2110.00061), [GriTS](https://www.microsoft.com/en-us/research/publication/grits-grid-table-similarity-metric-for-table-structure-recognition/)
13. **Benchmark splits must reflect real deployment drift.** Public KIE benchmarks can overstate generalization when templates leak across train/test. A study found 75% template replication in SROIE’s official test set and 16% in FUNSD, with F1 drops after resampling to remove template overlap. Production eval sets should stratify by vendor/template/doc type and include unseen-template and time-based regression splits. [Benchmark bias study](https://ar5iv.labs.arxiv.org/html/2304.14936)
14. **Use existing benchmarks for calibration but build a task-specific gold set.** FUNSD, SROIE, CORD, Kleister, DocILE, PubTables-1M, SOB, LLMStructBench, and ExtractBench cover useful pieces, but none exactly matches a production schema, PDF mix, evidence policy, and acceptable tolerances. DocILE adds large-scale business-document KILE/LIR tasks; Kleister targets long complex documents and normalization/business logic; ExtractBench is closest for end-to-end PDF-to-nested-JSON evaluation. [DocILE](https://docile.rossum.ai/), [Kleister](https://ar5iv.labs.arxiv.org/html/2003.02356), [FUNSD](https://ar5iv.labs.arxiv.org/html/1905.13538), [ExtractBench](https://arxiv.org/html/2602.12247)
15. **Production metrics should include operations, not just accuracy.** Track: parse success, schema-valid rate, invalid-schema rate, field precision/recall/F1, exact/semantic/numeric/date-normalized match, table-cell accuracy, evidence correctness, unsupported-value/hallucination rate, omission rate, null correctness, duplicate/spurious array items, confidence calibration/human-review deferral rate, cost/page, latency/page and latency/document, retry rate, provider/page-limit failures, and regression deltas by document class/model version.
16. **Recommended acceptance workflow:** (a) validate JSON schema/types; (b) normalize values; (c) verify required evidence exists and supports each value; (d) apply deterministic business rules; (e) auto-accept only high-confidence fields/documents; (f) route low-confidence/high-value fields to human review; (g) feed adjudicated corrections into a locked regression set.

## Gaps
- Provider internals for native PDF parsing, OCR quality, and grammar-constrained decoding are opaque and can change without notice; run provider-specific regression tests.
- No public benchmark fully covers end-to-end PDF image input + large enterprise schemas + field evidence + cost/latency/human review; build an internal gold set.
- Semantic-match and evidence-correctness judging still need human calibration and periodic audit; LLM judges can be biased or over/under-strict.
- Many 2026 benchmarks are new/preprint; validate claims against your own document distribution before adopting conclusions.
