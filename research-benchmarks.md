# Research: Spreadsheet LLM agent benchmarks and academic evaluation

## Summary
Spreadsheet-agent benchmarks are moving from small, synthetic, single-table tasks toward real workbooks with multi-table layouts, formatting, formulas, and OJ-style execution tests. Reported pass rates remain low on hard real-world manipulation: original SpreadsheetBench put GPT-4o at ~17% and Copilot in Excel at ~20%, while newer agent frameworks improve to ~35-42% on SpreadsheetBench and ~80% on the smaller SheetBench QA subset, still below human/expert levels. Product implication: a useful spreadsheet agent needs tool execution, structural/visual understanding, validation loops, and narrowly scoped UX with inspectable outputs rather than one-shot LLM answers.

## Findings

1. **SpreadsheetBench is the strongest public benchmark for real-world spreadsheet manipulation.** It contains 912 instructions and 2,729 test cases derived from Excel forums, averaging ~3 tests per instruction, with 10 manipulation categories; 35.7% of sheets contain multiple tables and 42.7% contain non-standard relational tables. Its key innovation is OJ-style evaluation: one generated solution must pass multiple value-varied spreadsheet cases, with soft and hard restriction scores. Reported model scores range from 0.05% to 23.65%; GPT-4o is ~16.96% soft / 13.27% hard, Copilot in Excel ~20% on a sampled evaluation, and humans ~71.33% soft / 62.00% hard. [SpreadsheetBench paper](https://arxiv.org/html/2406.14991v2), [SpreadsheetAgent results table quoting SpreadsheetBench](https://arxiv.org/html/2604.12282v1)

2. **SpreadsheetBench exposes product-critical failure modes: structure reading, coding robustness, and generalization.** Performance drops on large row/column counts, multiple tables, and non-standard structures. Adding more preview rows does not reliably help; multi-round execution feedback helps some models, but ReAct-style ad hoc retrieval can waste context or retrieve the wrong regions. The authors found exact-match evaluation has low false positives but some false negatives from extra generated content, which matters when designing automated grading and regression tests. [SpreadsheetBench paper](https://arxiv.org/html/2406.14991v2)

3. **SheetCopilot benchmark is earlier, smaller, and more software-control oriented.** SheetCopilot built 221 tasks over 28 workbooks, adapted from SuperUser questions plus self-instruct-like task generation, and evaluates by executing atomic spreadsheet actions and comparing necessary final-sheet properties. SheetCopilot with GPT-3.5 achieved 87.3% Exec@1 and 44.3% Pass@1; GPT-4 on a 10% subset achieved 55.0% Pass@1; a VBA baseline achieved 77.8% Exec@1 but only 16.3% Pass@1. Its limitations are that tasks are simpler, largely synthetic/adapted to benchmark workbooks, and atomic actions may not cover arbitrary spreadsheet behavior. [SheetCopilot NeurIPS 2023](https://proceedings.neurips.cc/paper_files/paper/2023/file/0ff30c4bf31db0119a6219e0d250e037-Paper-Conference.pdf)

4. **SheetRM and SheetAgent target long-horizon reasoning-dependent manipulation.** SheetRM has 317 tasks, 1,625 subtasks, 137 sheets, and averages 300.82 rows and 26.23 columns per file. It covers 5 broad operation categories / 36 subtypes plus reasoning challenges: complex computation logic, vague requirements, incoherent data format, and information extraction. Its procedure evaluation uses checklists of fine-grained criteria, so it can score full task Pass@1 and subtask SubPass@1. SheetAgent combines a Python Planner, SQL Informer, and code Retriever; on SheetRM, SheetAgent GPT-3.5 achieved 92.4 Exec@1 / 31.2 Pass@1 / 69.8 SubPass@1, GPT-4 achieved 44.8 Pass@1 / 77.0 SubPass@1, GPT-4o 46.1 Pass@1, and GPT-o1 62.5 Pass@1. SheetCopilot GPT-4 achieved only 2.2 Pass@1 / 30.7 SubPass@1 on SheetRM. [SheetAgent / SheetRM paper](https://arxiv.org/pdf/2403.03636)

5. **SheetAgent’s ablations point to architecture choices that matter.** Removing the Informer drops SheetRM Pass@1 from 31.2 to 13.2; removing the Retriever drops it to 19.9; removing both drops it to 11.4. JSON table representation outperformed DFLoader, Markdown, and HTML on WTQ/SheetRM in their setup. Product implication: keep a synchronized symbolic data view, use targeted queries rather than dumping the workbook, and maintain a retrieval library of verified code patterns. [SheetAgent / SheetRM paper](https://arxiv.org/pdf/2403.03636)

6. **SpreadsheetLLM / SheetEncoder is about encoding, not end-to-end agent control.** It addresses token limits and 2D layout by compressing spreadsheets with structural-anchor compression, inverse index translation, and data-format-aware aggregation. It reports a 25× average compression ratio; in spreadsheet table detection, GPT-4 in-context performance improved by 25.6% over vanilla serialization, and a fine-tuned LLM with SheetEncoder achieved 78.9% F1, 12.3 points above previous best. This supports a product design where workbook ingestion is a first-class subsystem, not just prompt serialization. [EMNLP 2024 SheetEncoder](https://aclanthology.org/2024.emnlp-main.1154/)

7. **TableLLM shows that table-focused fine-tuning can beat GPT-4o on spreadsheet-like tabular operations, but its benchmark is not full Excel automation.** TableLLM trains an 8B model with 73,157 constructed instances across document-embedded and spreadsheet-embedded tables, using reasoning extension and cross-way validation. Its TableLLM-bench has 4,898 tests: WikiTQ, FeTaQA, TAT-QA, WikiSQL, Spider, and 1,200 created query/update/merge/chart spreadsheet tasks. TableLLM achieved 86.74 average accuracy vs GPT-4o 84.79; in spreadsheet-embedded subsets it scored 89.6 WikiSQL / 81.05 Spider / 77.83 created, vs GPT-4o 84.00 / 69.53 / 77.83. Limitations: many spreadsheet tasks are CSV/table operations, with synthetic generation and LLM-judge components for some scoring. [TableLLM paper](https://arxiv.org/html/2403.19318v3)

8. **SheetBrain introduces SheetBench for complex spreadsheet QA/manipulation and demonstrates strong neuro-symbolic gains.** SheetBench comprises 69 challenging cases from 11 public sources, selected for large sheets, multi-table layouts, complex structures, and edit operations: 21 complex-table, 20 multi-table, 20 large-sheet, and 8 edit cases. SheetBrain uses understand → execute → validate: sheet summaries/problem insights, Python sandbox + Excel helper tools, and validation-triggered re-execution. On SheetBench, SheetBrain scored 55/69 overall versus BizChat Analyst 47/69, SheetAgent 35/69, vanilla GPT-4.1 34/69, ChatGPT 4o 30/69, and StructGPT 13/69. On public benchmarks, SheetBrain reported MultiHiertt 62.6, SpreadsheetBench 36.4 overall, RealHiTBench 78.3 overall, and SheetBench QA 80.3. [SheetBrain arXiv](https://arxiv.org/pdf/2510.19247), [AAAI page](https://ojs.aaai.org/index.php/AAAI/article/view/40671)

9. **SheetBrain ablations reinforce the value of structural summaries, validation, tools, and symbolic dataflow.** Removing understanding or validation each reduced SheetBench from 80.3 to 77.0; removing both reduced it to 73.8. In execution ablations, full tools achieved 79.1% on SheetBench; removing search/all tools dropped to 73.1%, and replacing code sandbox with JSON-style neural tool calling dropped to 65.1%. Encoding with cell/spatial structure substantially beat pure Markdown/HTML. Product implication: spreadsheet agents should store data in executable symbolic objects and expose inspection/search tools, not rely on raw text/tool-call transcripts. [SheetBrain arXiv](https://arxiv.org/pdf/2510.19247)

10. **The 2026 SpreadsheetAgent multi-agent/multi-format paper pushes SpreadsheetBench SOTA but still shows a large human gap.** This framework incrementally builds a YAML structural sketch using code execution, visual range inspection, LaTeX range inspection, and verification. On SpreadsheetBench, GPT-OSS-120B + SpreadsheetAgent achieved 38.16% soft / 31.47% hard overall, beating ChatGPT Agent 35.27% soft and GPT-4o 16.96% soft; Qwen3-Coder-480B + SpreadsheetAgent achieved 41.67% soft / 34.65% hard. Human performance remains 71.33% soft / 62.00% hard. The method averages 97.49 seconds and 19.54 agent calls per spreadsheet, implying latency/cost tradeoffs for products. [SpreadsheetAgent multi-format paper](https://arxiv.org/html/2604.12282v1)

11. **Commercial/non-academic “SheetBench-50” exists but should not be conflated with academic SheetBench.** HUD describes SheetBench-50 as a public financial-analyst-grade spreadsheet benchmark with 50 tasks, developed with Sepal AI, intended to evaluate agents on financial analyst workflows. Search-accessible material did not expose stable academic methodology, leaderboard scores, or detailed pass rates, so it is useful as a product-market signal but not as primary academic evidence. [HUD SheetBench-50 case study](https://www.hud.ai/case-studies/sheetbench-50)

12. **General table-reasoning benchmarks remain relevant but insufficient for spreadsheet products.** WikiTableQuestions, TabFact, FeTaQA, TAT-QA, HiTab, MultiHiertt, RealHiTBench, TableBench, and TableEval test important reasoning capabilities such as compositional QA, fact verification, free-form answers, finance table+text reasoning, hierarchical headers, and multi-table/multilingual settings. However, most use clean serialized tables and answer text rather than editing XLSX files, preserving formulas/styles, handling multiple worksheets, or producing durable workbook modifications. TableBench explicitly argues that industrial table use is more complex than academic TableQA and reports GPT-4 still far below humans. [FeTaQA](https://aclanthology.org/2022.tacl-1.3/), [TableBench AAAI](https://ojs.aaai.org/index.php/AAAI/article/view/34739), [TableLLM benchmark discussion](https://arxiv.org/html/2403.19318v3)

## Product implications

1. **Evaluate with executable workbooks, not chat answers.** Use OJ-style multi-case tests for each task, compare cell values/formulas/styles/charts in bounded output ranges, and include corner-case perturbations.
2. **Separate understanding from execution.** Build a workbook parser/encoder that identifies sheets, tables, headers, formulas, formatting, merged cells, charts, and named ranges before asking an LLM to solve.
3. **Use symbolic execution and sandboxing.** The best systems rely on Python/Excel APIs, SQL/pandas views, and controlled tools; one-shot natural language or raw Markdown table prompts are not reliable enough.
4. **Add validation and repair loops.** Validation modules materially improve reliability and should check structure, task satisfaction, and unintended changes before returning a workbook.
5. **Design for latency/cost.** Multi-agent approaches improve accuracy but may need ~20 tool/model calls and >1 minute per workbook in research settings; products should gate expensive workflows by task difficulty.
6. **Human-in-the-loop remains necessary for high-stakes spreadsheets.** Even the best reported public spreadsheet manipulation systems trail human experts substantially on SpreadsheetBench.

## Gaps

- Exact leaderboard values may change quickly, especially for SpreadsheetBench Verified and commercial agents; validate against current official leaderboards before procurement or publication.
- Some recent 2026 papers are arXiv/preprint or newly accepted and need independent replication.
- Public benchmarks still under-cover enterprise-specific needs: financial modeling audits, pivot tables, macros/VBA, protected sheets, external data connections, collaborative editing, and compliance logging.
- A product team should build an internal benchmark from real anonymized user workbooks, with task categories, risk labels, expected outputs, and regression tests for unintended workbook changes.
