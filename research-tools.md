# Research: Production tools for PDF/document parsing and fact extraction

## Summary
Production document extraction is best treated as a two-stage pipeline: (1) parse/OCR/layout/table extraction into an element model with page, bounding-box/span provenance and tool confidence where available; (2) run schema-constrained fact extraction over those elements, requiring source citations back to element IDs. For local/open-source, use specialist parsers by document type (PyMuPDF/pdfplumber/Camelot for born-digital PDFs and tables; OCRmyPDF/PaddleOCR for scans; GROBID for scientific papers; Docling/MinerU/Marker/Unstructured for RAG-ready Markdown/JSON). For managed IDP, Azure Document Intelligence, AWS Textract, and Google Document AI provide the strongest native confidence/provenance; Adobe PDF Extract is strong for PDF structure; LlamaParse is convenient for LLM/RAG parsing but should be wrapped with validation and provenance checks.

**Interpretation.** For born-digital PDFs, PyMuPDF/pdfplumber provide the most auditable low-level provenance; Camelot is table-specialized; GROBID is the best domain parser for scholarly articles. For scanned or visually complex PDFs, Docling, MinerU, Unstructured `hi_res`, Marker, and PaddleOCR/PP-Structure are more complete local pipelines, but only Docling/Unstructured emphasize reusable element/provenance models; most local tools lack calibrated confidence.

### 3. Structured fact extraction and validation layer

| Tool | Schema enforcement | Validation/retry | Provenance support | Best use | Failure modes |
|---|---|---|---|---|---|
| [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs) | Provider-native JSON Schema; `strict: true` makes model output adhere to supplied schema | Provider handles syntax/schema conformance; refusals are explicit | Not automatic: include `source_page`, `source_bbox`, `source_quote`, `evidence_element_ids` in your schema | High-reliability extraction from parsed text/images when using OpenAI models | Schema-valid does not mean factually correct. Must validate against source spans and handle refusals/unsupported schemas. |
| [Instructor](https://python.useinstructor.com/concepts/validation/) | Pydantic models over many providers | Pydantic validation, coercion, custom validators; validation failures can trigger retries | User-defined fields only | Lightweight typed extraction in Python; good for field/range validators | Retried outputs may still be unsupported by evidence; provider-specific structured-output quality varies. |
| [Guardrails AI](https://guardrailsai.com/guardrails/docs/api_reference_markdown/guards) | JSON Schema/Pydantic/RAIL-style schemas | Validators with pass/fail, reask/fix/filter actions; returns raw + validated output | User-defined fields; can validate citation fields | When business rules and safety/quality validators matter | More configuration/latency; validators enforce form/rules, not truth unless evidence validators are built. |
| [LangChain structured output](https://docs.langchain.com/oss/python/langchain/structured-output) | `ProviderStrategy` for native structured output or `ToolStrategy` for tool-calling schemas | Captures validated `structured_response`; tool strategy can handle errors | User-defined fields only | Framework integration across providers/agents | Abstraction can hide provider limits; always inspect raw output and validation errors for production. |

**Recommended extraction contract.** Define every extracted fact as `{value, normalized_value, confidence_or_quality, source_document_id, page, bbox_or_span, source_quote, parser_element_id, extraction_method, validation_status}`. If a parser lacks confidence, use a rule-based quality flag (`exact_quote_found`, `value_in_table_cell`, `multi_source_agreement`) rather than inventing numeric confidence.

### 4. Production architecture guidance

1. **Normalize all parsers to a common element model.** Minimal fields: `doc_id`, `page`, `element_id`, `type`, `text/html/markdown`, `bbox`, `char_span`, `reading_order`, `parser`, `parser_version`, `parser_confidence`, `parent/child relationships`. Azure/Textract/Google already return much of this; Docling/Unstructured are good local models; PyMuPDF/pdfplumber can populate low-level fields.
2. **Route by document class.** Use GROBID for scholarly papers; Camelot/pdfplumber/PyMuPDF for born-digital PDF tables; OCRmyPDF/PaddleOCR for scans; Docling/MinerU/Marker/Unstructured for mixed RAG corpora; managed IDP for regulated extraction with confidence and SLAs.
3. **Separate parsing confidence from fact confidence.** OCR confidence answers “was text recognized?”; entity confidence answers “did the IDP model identify the field?”; LLM schema validity answers “does output fit schema?” None alone proves the fact is true.
4. **Require evidence-bound extraction.** The LLM/validator should reject facts that cannot be quoted from the parsed elements. For table facts, store table cell coordinates and row/column labels.
5. **Build failure triage.** Route low confidence, missing provenance, unquoted values, conflicting parser outputs, empty OCR pages, huge tables, and LLM refusals to human review or a second parser.

## Gaps
- Confidence calibration is not comparable across tools; many local parsers do not expose calibrated confidence. A production evaluation set is needed to map parser-specific scores/heuristics to business acceptance thresholds.
- Exact throughput/cost depends heavily on hardware, page complexity, cloud region, and model version. Benchmark with representative documents before standardizing.
- LLM/VLM parsers and schema extractors can produce schema-valid but unsupported facts. Always require source quote + page/bbox/span validation.
