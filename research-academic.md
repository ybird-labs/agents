# Research: Academic literature and benchmarks for production-grade PDF/document fact extraction with provenance

## Summary
Production-grade fact extraction from PDFs should be treated as a **document parsing + evidence localization + schema-constrained extraction + validation** problem, not a single end-to-end LLM prompt. The strongest evidence is that modern systems still fail on realistic multi-page parsing, large schemas, table/form structure, and especially **attribution/provenance**: READoc shows gaps in PDF-to-Markdown DSE, ExtractBench shows frontier-model failures on broad PDF-to-JSON schemas, and newer attribution benchmarks show correct answers can cite the wrong source region.

## Findings

1. **READoc is validated and directly relevant for parser-level evaluation.** — The requested “READoc ACL 2025 Findings 1128” is real: ACL Anthology lists *READoc: A Unified Benchmark for Realistic Document Structured Extraction*, Findings of ACL 2025, pages 21889–21905, DOI 10.18653/v1/2025.findings-acl.1128. It defines DSE as converting complete PDFs into semantically rich Markdown and uses 3,576 real-world documents from arXiv, GitHub, and Zenodo; its S3 evaluation suite scores text, headings/ToC, formulas, tables, and reading order. **Strength:** realistic full-document parsing benchmark. **Limit:** evaluates Markdown structural fidelity, not field-level JSON facts or per-fact provenance. **Architecture relevance:** use READoc-style parser scoring to qualify the ingestion layer before IE. [ACL](https://aclanthology.org/2025.findings-acl.1128/) [arXiv](https://arxiv.org/html/2409.05137)

2. **Document Parsing Unveiled is validated as a broad survey, useful for design taxonomy rather than benchmarking.** — arXiv 2410.21169 surveys modular document parsing pipelines and end-to-end VLM/DELM approaches; it covers layout detection, OCR, formulas, tables, charts, datasets, metrics, and tools, and explicitly notes challenges in module integration, reading order, dense text, complex tables, and high deployment cost. **Strength:** good map of the parsing stack. **Limit:** survey only; no unified production benchmark or provenance metric. **Architecture relevance:** supports a modular design with separate layout/OCR/table/formula/chart components plus a normalized intermediate representation. [arXiv](https://arxiv.org/html/2410.21169v1)

3. **ExtractBench is validated and is the closest benchmark for enterprise PDF-to-JSON extraction.** — arXiv 2602.12247 introduces 35 PDF+JSON-Schema+gold-JSON tasks across five domains, 2,076 pages, and 12,867 evaluatable fields; its schema-driven evaluator supports per-field metrics, semantic array alignment, and missing/null/hallucination distinction. It reports frontier models producing only 51% valid JSON overall and 0% valid output on a 369-field SEC schema; structured-output APIs lowered validity from 51% to 37% in their experiments. **Strength:** production-like nested JSON extraction and evaluation methodology. **Limit:** small diagnostic dataset; provenance is evaluated as correctness vs gold, not source-region grounding. **Architecture relevance:** decompose large schemas, use per-field metrics, track omissions vs hallucinations, and do not rely solely on provider structured-output modes for large schemas. [arXiv](https://arxiv.org/html/2602.12247) [GitHub](https://github.com/ContextualAI/extract-bench)

4. **Provenance must be a first-class output, not a post-hoc citation.** — CiteVQA requires answers plus element-level bounding-box citations and introduces Strict Attributed Accuracy, giving credit only when both answer and evidence are correct. It reports “Attribution Hallucination”: models can answer correctly but cite wrong regions; the best closed model reached 76.0 SAA, while the strongest open-source model reached 22.5. BoundingDocs similarly unifies document QA/IE datasets and adds answer bounding boxes; it finds off-the-shelf models’ answer localization is effectively near-zero by IoU despite answer retrieval ability. **Strength:** directly tests provenance. **Limit:** QA framing, not arbitrary JSON extraction. **Architecture relevance:** every extracted fact should carry `{document_id, page, bbox/span, quote, parser_version, confidence}` and be scored with answer+evidence joint metrics. [CiteVQA](https://arxiv.org/html/2605.12882) [BoundingDocs](https://arxiv.org/html/2501.03403v2)

5. **Layout-aware encoders are proven baselines for forms/receipts but are not enough for full production extraction.** — LayoutLM jointly models text and 2D layout and improved SOTA on form understanding, receipt understanding, and document classification; LayoutLMv3 unifies text/image masking and adds word-patch alignment, reaching SOTA on text-centric tasks like FUNSD/CORD/DocVQA and image-centric tasks like RVL-CDIP/PubLayNet. DocFormer similarly combines text, vision, and spatial features via multimodal attention and reports SOTA on four VDU datasets. **Strength:** strong for token/entity extraction where OCR tokens and boxes are available. **Limit:** typically page/task-specific; depend on OCR and labeled layouts; do not natively emit auditable JSON with evidence. **Architecture relevance:** useful for evidence candidate generation, key-value/entity extraction, and reranking localized spans. [LayoutLM](https://arxiv.org/abs/1912.13318) [LayoutLMv3](https://arxiv.org/abs/2204.08387) [DocFormer](https://arxiv.org/abs/2106.11539)

6. **OCR-free generative document models reduce OCR dependency but do not solve provenance.** — Donut is an OCR-free Transformer for visual document understanding, motivated by OCR cost, inflexibility, and error propagation, and reports speed/accuracy gains with released code and synthetic data. Nougat converts scientific PDFs/pages into markup, especially preserving formulas and scientific semantics. **Strength:** useful when OCR is weak, for document-to-markup and domain-specific parsing. **Limit:** generative models can omit, reorder, or hallucinate content; Nougat is academic-document-focused; neither alone gives reliable field-level provenance. **Architecture relevance:** use as one parser candidate, but preserve source images/coordinates and validate generated markup against layout/OCR evidence. [Donut](https://arxiv.org/abs/2111.15664) [Nougat](https://arxiv.org/abs/2308.13418)

7. **Core datasets validate individual modules, not the full system.** — DocLayNet provides 80,863 manually annotated pages across diverse sources with 11 layout classes and inter-annotator agreement; PubLayNet provides 360k+ scientific article page images from 1M+ PubMed Central PDFs with layout annotations. FUNSD has 199 noisy scanned forms with text blocks, entity labels, and links; SROIE has 1,000 scanned receipts and tasks for localization, OCR, and key information extraction; PubTables-1M has nearly 1M scientific tables with table detection, structure, and functional-analysis labels. **Strength:** high-value supervised training/evaluation for layout, forms, receipts, and tables. **Limit:** narrow, often single-page or domain-specific, and generally not end-to-end fact+provenance benchmarks. **Architecture relevance:** use these to test submodules: layout detector, OCR/entity linker, receipt/form extractor, and table structure recognizer. [DocLayNet](https://arxiv.org/abs/2206.01062) [PubLayNet](https://arxiv.org/abs/1908.07836) [FUNSD](https://arxiv.org/abs/1905.13538) [SROIE](https://arxiv.org/abs/2103.10213) [PubTables-1M](https://openaccess.thecvf.com/content/CVPR2022/html/Smock_PubTables-1M_Towards_Comprehensive_Table_Extraction_From_Unstructured_Documents_CVPR_2022_paper.html)

8. **Generative IE and OpenIE are relevant to fact modeling, but document provenance requires additional grounding.** — The LLMs-for-generative-IE survey organizes entity/relation/event extraction with LLMs and identifies emerging techniques and directions. Stanford OpenIE extracts open-domain relation triples from text without a predefined schema, e.g. `(subject; relation; object)`, by clause splitting and shortening before triple segmentation. **Strength:** useful for extracting candidate facts/triples once text is reliably parsed. **Limit:** text-only IE loses page/layout/table provenance unless the text is tied back to spans/boxes; OpenIE relations are unnormalized and noisy. **Architecture relevance:** run IE over provenance-carrying chunks/spans, then normalize/validate against schemas and keep evidence links. [LLM IE Survey](https://arxiv.org/abs/2312.17617) [Stanford OpenIE](https://nlp.stanford.edu/software/openie.html)

## Architecture implications

- **Canonical document IR:** store pages, blocks, lines, tokens, tables, figures, reading order, OCR text, normalized coordinates, parser confidence, and source byte/image references.
- **Parser ensemble + validation:** combine native PDF extraction, OCR, layout/table detectors, and optional generative parsers; benchmark with READoc/DocLayNet/PubLayNet/PubTables before downstream extraction.
- **Evidence-first extraction:** retrieve/localize candidate evidence regions first; extract facts from bounded evidence, not whole PDFs when possible.
- **Schema-driven extraction:** use JSON Schema/Pydantic-like schemas with per-field evaluation rules, decomposition for wide schemas, and explicit null/missing semantics as in ExtractBench.
- **Provenance contract:** every fact should include value, normalized value, quote/snippet, page, bbox/token span, table cell coordinates when applicable, document version, extraction method, and confidence.
- **Evaluation:** report field accuracy, valid JSON, omissions, hallucinations, array alignment, and provenance IoU/Strict Attributed Accuracy-style metrics.

## Gaps

- No single benchmark fully covers **PDF-to-JSON fact extraction with field-level provenance** across arbitrary domains, large schemas, tables, scans, and multi-document evidence.
- ExtractBench is strong for JSON correctness but weak on source grounding; CiteVQA/BoundingDocs are strong on grounding but framed as QA rather than arbitrary schema extraction.
- Recommended next step: build an internal gold set with `{fact, schema field, normalized value, quote, page, bbox/table-cell}` and evaluate both extraction accuracy and provenance fidelity end-to-end.
