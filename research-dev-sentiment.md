# Research: Developer sentiment and implementation reports for AI spreadsheet agents

## Summary
Developer sentiment is converging on: **do not build a spreadsheet agent by dumping XLSX contents into an LLM or by driving screenshots/UI**. The practical recommendation is to use an existing workbook-aware substrate (Excel add-in/Graph if you need true Excel fidelity, or a local CLI/MCP/SDK such as spreadsheet-kit / mcp-excel for agent workflows) and only custom-build the orchestration layer around narrow tools, verification, and sandboxing. The hardest recurring implementation issues are formula recalculation/fidelity, table/region detection, context-window pressure, unsafe file/formula/code execution, and ergonomic tool surfaces that let agents inspect/modify/verify without over-reading.

## Findings
1. **Existing tools are preferred unless the product’s differentiator is the spreadsheet engine itself.** Mature-ish projects now expose exactly the primitives agent builders keep reinventing: workbook/sheet discovery, region/table detection, range reads, formula tracing, safe edits, recalculation, diffs, proof/verification, and pagination. spreadsheet-kit explicitly positions itself as a “safe, inspectable, token-efficient” interaction layer with CLI, MCP, SDK, and WASM surfaces, plus dry-run, recalc, diff, proof, sessions, and formula diagnostics. [spreadsheet-kit README](https://github.com/PSU3D0/spreadsheet-mcp/blob/main/README.md)

2. **Use Excel-native automation when Excel fidelity matters.** Claude for Excel’s docs emphasize working inside Excel, preserving formula relationships, cell-level citations, native operations, and dependent recalculation, but still label the feature beta and not recommended for final/audit-critical work without review; unsupported areas include data tables, macros, and VBA operations. This is a strong signal that even vendors embedded in Excel are cautious about fidelity and review. [Claude for Excel docs](https://claude.com/docs/office-agents/excel)

3. **Formula calculation is the biggest technical trap.** openpyxl “never evaluates formula”; it only writes/preserves formulas and can read cached values if another app calculated them. libxlsxwriter likewise does not calculate formulas; it stores `0` and asks Excel to recalc on open, which fails for viewers/PDF converters/some apps. SheetJS supports parsing/writing formulas but says it “will not automatically compute formula results.” [openpyxl docs](https://openpyxl.readthedocs.io/en/stable/simple_formulae.html), [libxlsxwriter docs](https://libxlsxwriter.github.io/working_with_formulas.html), [SheetJS formula docs](https://docs.sheetjs.com/docs/csf/features/formulae/)

4. **LibreOffice headless is useful but not Excel-equivalent.** Several projects use LibreOffice for server-side recalc, but LibreOffice/Calc and Excel can produce different numeric results due to rounding, operand order, and function behavior; Wikibooks also flags XLSM compatibility issues. spreadsheet-kit exposes pluggable recalc backends: native Rust “Formualizer” by default and LibreOffice for maximum compatibility/screenshot flows, implicitly acknowledging a tradeoff between dependency weight and fidelity. [LibreOffice/Calc compatibility notes](https://en.wikibooks.org/wiki/LibreOffice/Calc/Excel_Compatibility_and_Problems), [spreadsheet-kit README](https://github.com/PSU3D0/spreadsheet-mcp/blob/main/README.md)

5. **Context-window pressure pushes designs toward atomic operations, SQL-like querying, pagination, and compact encodings.** mcp-excel’s README argues that most AI Excel tools dump raw data into context, causing overflow and miscalculation; it exposes pandas-backed atomic operations like filter/count, group-by, aggregation, profiling, and overlap analysis so the model receives results instead of rows. Microsoft’s SpreadsheetLLM paper reports vanilla spreadsheet serialization is impractical under token limits and achieves about 25× compression / 96% token reduction with structure-aware compression, improving table detection. [mcp-excel README](https://github.com/jwadow/mcp-excel/blob/main/README.md), [SpreadsheetLLM paper](https://arxiv.org/pdf/2407.09025)

6. **Table/region detection is a first-class capability, not a nice-to-have.** Chunkr, Reducto-style APIs, spreadsheet-kit, and SpreadsheetLLM all frame spreadsheets as multiple logical regions/tables with headers, metadata, blank regions, formulas, merges, and layout cues. Chunkr returns spreadsheet-specific fields like sheet name, range, individual cells, formulas, values, and header range; spreadsheet-kit starts workflows with sheet overview / region detection before exact reads. [Chunkr Excel parser docs](https://docs.chunkr.ai/pages/v1/excel-parser/overview), [spreadsheet-kit README](https://github.com/PSU3D0/spreadsheet-mcp/blob/main/README.md)

7. **Workbook APIs beat screenshots/UI automation for developer trust.** A practitioner blog argues screenshots cannot provide stable contracts for whether values came from formulas, whether recalculation happened, whether row insertions shifted references, whether hidden sheets/names changed, or whether the saved workbook round-trips. The recommended pattern is explicit workbook state: load/create, edit, recalculate, exact readback, persist/restore, verify. [Dev.to workbook API post](https://dev.to/gregkonush/why-agents-need-workbook-apis-instead-of-spreadsheet-screenshots-3d61)

8. **MCP tool security is currently a real pain point.** The popular `excel-mcp-server` had reports/advisories around path traversal and arbitrary file read/write in remote transports, plus formula injection concerns. One issue describes arbitrary file paths and unrestricted formulas such as `WEBSERVICE`/`HYPERLINK`; a GitHub advisory says versions `<=0.1.7` let unauthenticated network attackers read/write/overwrite files via crafted `filepath` arguments when exposed over SSE/HTTP. [excel-mcp-server issue #120](https://github.com/haris-musa/excel-mcp-server/issues/120), [GitHub advisory GHSA-j98m-w3xp-9f56](https://github.com/haris-musa/excel-mcp-server/security/advisories/GHSA-j98m-w3xp-9f56)

9. **Prompt injection is specifically relevant to spreadsheet agents.** Claude for Excel explicitly warns that external templates/vendor files/data imports may contain prompt injections that can try to extract sensitive information, modify critical data, or perform destructive actions; risky operations require confirmation. This applies equally to custom MCP agents because cell text, comments, formulas, sheet names, and hidden sheets can become tool output fed back into the model. [Claude for Excel docs](https://claude.com/docs/office-agents/excel)

10. **Generated code and generated SQL need sandboxing.** PandasAI’s security docs state that it executes LLM-generated Python and strongly recommends Docker sandboxing for public-facing, untrusted, production, sensitive, and multi-tenant use cases. DuckDB’s security docs warn to treat SQL like Bash/Python and not execute untrusted SQL without sandboxing, recommending duckdb-wasm or isolated containers. [PandasAI security docs](https://docs.pandas-ai.com/v3/privacy-security), [DuckDB security docs](https://duckdb.org/docs/stable/operations_manual/securing_duckdb/overview.html)

11. **DuckDB/pandas patterns are popular for analysis, but they shift fidelity risk.** HN and GitHub reports show developers choosing DuckDB/WASM/OPFS or pandas-backed MCP tools to keep raw data local and send only schema/results to AI. This works well for table-like analytics and large CSV/XLSX ingestion, but it is not a full workbook engine: formulas, styles, named ranges, pivot tables, merged headers, hidden sheets, and exact Excel recalculation semantics need separate handling. [HN DuckDB WASM data analyst](https://news.ycombinator.com/item?id=47331441), [mcp-excel README](https://github.com/jwadow/mcp-excel/blob/main/README.md)

12. **XLSX parsing performance and completeness remain pain points.** DuckDB’s SheetReader work says existing spreadsheet loaders use general-purpose XML parsers ill-suited to XLSX, causing CPU and memory bottlenecks; their specialized parser reports up to order-of-magnitude speedup and multi-GB memory savings. SheetJS docs also highlight nuanced formula storage differences, locale normalization, future-function prefixes, and unsupported/calculation caveats. [DuckDB SheetReader article](https://duckdb.org/library/practical-spreadsheet-parsing-with-sheetreader/), [SheetJS formula docs](https://docs.sheetjs.com/docs/csf/features/formulae/)

## Recommendations
1. **Adopt, don’t invent, the workbook substrate.** Start with spreadsheet-kit or a comparable MCP/CLI for local workbook workflows; use Excel add-ins/Office.js/Graph for workflows where exact Excel behavior matters. Custom-build only the agent policy, UX, domain workflows, and verification gates.
2. **Design around a three-lane architecture:**
   - **Workbook lane:** exact cells, formulas, styles, names, sheets, diffs, recalc, proof.
   - **Analytics lane:** DuckDB/pandas for table-like summaries, filters, joins, profiling, charts.
   - **LLM lane:** planning and explanation only; never raw full-workbook ingestion by default.
3. **Make recalculation explicit.** After edits, run a known backend, capture errors, compare target cells, and disclose fidelity mode: Excel-native, LibreOffice, native formula engine, or “cached values only.”
4. **Prefer compact/atomic tools over broad reads.** Provide `describe`, `sheet_overview`, `find`, `read_range`, `read_table`, `profile`, `aggregate`, `diff`, and `proof` tools with pagination and row/column limits.
5. **Treat every workbook as hostile input.** Strip or gate dangerous formulas, validate paths against a workspace root, default to read-only or dry-run, require confirmation for destructive writes, and isolate file/code/SQL execution.
6. **Keep MCP surface ergonomic but small.** Too many schemas consume context; too few tools force overbroad reads. A CLI-style single tool with subcommands can be cheaper for coding agents; MCP is better for cached multi-turn sessions.
7. **Build fixtures early.** Maintain a regression corpus covering formulas, dynamic arrays, merged cells, multiple tables per sheet, hidden sheets, named ranges, pivots/charts, xlsm, locale formulas, and LibreOffice-vs-Excel divergences.

## Gaps
- Public Reddit/HN sentiment specifically on “AI spreadsheet agents” is sparse; most evidence is from product READMEs, GitHub issues, security advisories, and implementation posts.
- Few public benchmarks compare Excel-native, LibreOffice, and open-source formula engines across real financial workbooks.
- Need hands-on evaluation of candidate tools on Exeboard’s target files: formula-heavy financial models vs table-like operational sheets will lead to different architecture choices.
