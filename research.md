# Research: PyMuPDF PDF-to-IR parser for evidence-backed summarization

## Summary
Use `import pymupdf` and build the IR from `page.get_text("dict", sort=True)` with image extraction disabled, aggregating PyMuPDF span text into line-level `TextSpan`s. Line-level spans give stable, citation-friendly provenance with page, reading order, canonical `char_start`/`char_end`, and a usable line bbox, while avoiding both block-level coarseness and raw character/word-level reconstruction costs.

## Findings
1. **Recommended parser shape** — Open with `pymupdf.open(path)` in a context manager; iterate pages in document order; call `page.get_text("dict", sort=True, flags=pymupdf.TEXTFLAGS_DICT & ~pymupdf.TEXT_PRESERVE_IMAGES)`; skip non-text blocks (`block["type"] != 0`); for each line concatenate `span["text"]` values; append deterministic separators to a single canonical `content`; emit one `TextSpan` per non-empty line with 1-based `page_number`, global `reading_order`, `[char_start, char_end)`, and `bbox=tuple(line["bbox"])`. PyMuPDF’s TextPage hierarchy is page → block → line → span → char, and `dict` exposes block/line/span bboxes and span text without requiring raw character lists. [PyMuPDF TextPage](https://pymupdf.readthedocs.io/en/latest/textpage.html)
2. **Use line-level IR spans as the default granularity** — PyMuPDF spans are not semantic spans; they are adjacent characters with identical font properties, so a bold word or font change can fragment one sentence/line. Blocks are roughly paragraphs and too coarse for precise citations; words have bboxes but omit whitespace as units and make canonical text reconstruction harder; `rawdict` gives per-character provenance but is heavier. Line-level aggregation is the best default compromise for evidence-backed summaries: cite page + line span/offsets, chunk by adjacent lines, and use the line bbox for UI highlighting. [Appendix 1: Details on Text Extraction](https://pymupdf.readthedocs.io/en/latest/app1.html)
3. **Prefer `dict` over `rawdict` for baseline parsing** — `rawdict` is an information superset of `dict` and replaces span `text` with a `chars` list, enabling char-level bboxes when needed. The docs’ performance table shows `DICT` and `RAWDICT` are among the slower variants when images are included, and explicitly warns that images greatly increase time and data size; excluding images improves performance and memory use. Use `rawdict` only behind an option for exact character-to-bbox mapping, OCR debugging, or high-precision highlighting. [Appendix 1: RAWDICT and performance](https://pymupdf.readthedocs.io/en/latest/app1.html)
4. **Do not use `blocks` as the canonical IR source** — `page.get_text("blocks")` is high-speed and returns block bbox plus concatenated block text, but it loses line/span structure needed for robust offsets, fine-grained citations, and future layout diagnostics. It can be useful as a fast smoke-test or fallback, not as the evidence provenance representation. [TextPage.extractBLOCKS](https://pymupdf.readthedocs.io/en/latest/textpage.html)
5. **Do not use `words` as the canonical IR source** — `page.get_text("words")` is high-speed and returns `(x0, y0, x1, y1, word, block_no, line_no, word_no)`, with optional extra delimiters. It is useful for hit-testing, search alignment, table heuristics, or locating terms inside rectangles, but because separators are not themselves represented as words, it is a poor primary source for canonical document content and char offsets. [TextPage.extractWORDS](https://pymupdf.readthedocs.io/en/latest/textpage.html)
6. **Reading order: use `sort=True`, but treat it as heuristic** — PyMuPDF says plain text is otherwise returned in the original creator-specified order, which may not be natural. `sort=True` sorts vertically then horizontally and “in many cases” suffices for natural reading order. This is appropriate for the first parser version, but multi-column, tables, sidebars, headers/footers, and complex PDFs still need regression fixtures and possibly custom layout logic or PyMuPDF4LLM evaluation. [TextPage sort parameter](https://pymupdf.readthedocs.io/en/latest/textpage.html)
7. **Canonical content and offsets should be parser-owned** — Do not call `page.get_text("text")` separately to create `DocumentIR.content`, because it can diverge from the text used to create spans. Instead, build content from the emitted line texts in exactly the same pass: append line text, `\n` between lines, blank-line separators between blocks if desired, and `\f\n` or another explicit page separator between pages. Record offsets before/after each line’s text only, excluding parser-inserted separators from any span. Use Python string indices consistently and document that offsets are into normalized canonical content, not PDF byte offsets.
8. **Coordinate model to store** — Store bboxes as four floats `(x0, y0, x1, y1)` in PyMuPDF page coordinates: units are points (72 points = 1 inch), y increases downward, and rectangles are axis-aligned. PyMuPDF notes most returned coordinates, including `Page.get_text()` coordinates, refer to the unrotated page; `Page.rect`/`bound()` reflect page rotation. Store page width/height and/or note `coordinate_space="pymupdf_unrotated_points"` in `DocumentIR` metadata if available. [Rect documentation](https://pymupdf.readthedocs.io/en/latest/rect.html), [Page coordinate note](https://pymupdf.readthedocs.io/en/latest/page.html)
9. **Rotated or non-horizontal text risk** — `dict`/`rawdict` return bboxes, not quads. Bboxes are sufficient for most horizontal text, but line dictionaries include `dir`; if `line["dir"] != (1, 0)`, the visual text is rotated and a rectangular bbox may be imprecise for highlighting. PyMuPDF provides `recover_quad()`, `recover_line_quad()`, and related helpers for accurate annotation/highlight geometry. Since `TextSpan` only has optional `bbox`, either accept approximate bboxes for v1 or extend metadata later for quads. [TextPage dictionary structure](https://pymupdf.readthedocs.io/en/latest/textpage.html), [Recipes: non-horizontal text](https://pymupdf.readthedocs.io/en/latest/recipes-text.html)
10. **Use modern import name** — New code should `import pymupdf`. The docs state old versions used `fitz`, newer versions use `pymupdf`, and `fitz` is a fallback for old code. Installation docs also warn that `import fitz` can collide with an unrelated PyPI `fitz` package and cause `ModuleNotFoundError: No module named 'frontend'`. [Tutorial: importing bindings](https://pymupdf.readthedocs.io/en/latest/tutorial.html), [Installation problems](https://pymupdf.readthedocs.io/en/latest/installation.html)
11. **Testing strategy with generated PDFs** — Use pytest `tmp_path` and PyMuPDF itself: `doc = pymupdf.open()`, `page = doc.new_page()`, `page.insert_text(...)` / `page.insert_textbox(...)`, `doc.save(tmp_path / "case.pdf")`, then call `DocumentParser.parse`. Test simple text, multiple pages, blank pages, same-line style/font changes, two columns/top-left ordering, page rotation, non-horizontal text if supported, and empty/scanned PDFs. Generated PDFs are deterministic and dependency-light, but supplement them with a few real fixture PDFs because synthetic PDFs will not cover all creator-order, font encoding, ligature, OCR, table, and multi-column failures. [Tutorial: opening/creating documents](https://pymupdf.readthedocs.io/en/latest/tutorial.html), [Recipes: insert text](https://pymupdf.readthedocs.io/en/latest/recipes-text.html)
12. **Licensing and deployment risk** — PyMuPDF is dual-licensed under AGPL or commercial terms. Confirm the project can comply with AGPL obligations or obtain the appropriate commercial license before shipping a product or hosted service using it. [PyMuPDF README license section](https://github.com/pymupdf/PyMuPDF/blob/main/README.md)

## Recommended design
- **Extraction:** `dict`, `sort=True`, image-preserving flag disabled.
- **IR granularity:** one `TextSpan` per extracted text line, formed by concatenating its PyMuPDF spans.
- **Offsets:** build `DocumentIR.content` and `TextSpan` offsets in the same loop; offsets are half-open character indices into canonical content.
- **Provenance:** store 1-based page numbers, global reading order, and line bboxes; optionally keep page dimensions / coordinate-space metadata.
- **Optional future modes:** `rawdict` for char-level bbox mapping; `words` for hit-testing/search/table logic; PyMuPDF4LLM or custom layout sorting for complex multi-column Markdown/RAG preprocessing.

## Gaps
- `sort=True` is not a full layout-analysis algorithm; confidence is lower for multi-column pages, tables, marginalia, headers/footers, rotated text, and PDFs with unusual content-stream order. Add representative real-world fixtures and compare output against expected reading order.
- PyMuPDF text extraction is not OCR by default. Scanned PDFs may produce no text unless OCR is added separately.
- `TextSpan` only supports rectangular bboxes, so exact provenance for rotated/skewed text may require extending the IR with quads or a secondary geometry table.
