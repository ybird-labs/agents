# Implemented Layout IR Expert Review

Research basis used for this review: Docling `ProvenanceItem`/DoclingDocument provenance model (page number, bbox, charspan; https://github.com/docling-project/docling-core/blob/main/docling_core/types/doc/document.py and https://docling-project-docling.mintlify.app/concepts/docling-document), ACL/ACM 2025 citation-attribution work distinguishing citation correctness from faithful attribution (https://dl.acm.org/doi/10.1145/3731120.3744592; https://aclanthology.org/2025.findings-emnlp.339.pdf), recent grounded summarization work emphasizing evidence spans (https://arxiv.org/pdf/2601.08472; https://aclanthology.org/2025.emnlp-main.95.pdf), and Pydantic strict/schema-boundary validation guidance (https://pydantic.dev/docs/validation/latest/concepts/strict_mode/).

Verdict: CHANGE before treating this as a production-ready layout IR contract. The direction is sound, but the schema still permits invalid provenance and structure. The reported 196 passing tests are not sufficient for production suitability; they cover many intended happy/negative paths, but not the provenance-contract gaps below. I could not independently run the suite in this environment because `pytest` is not installed (`pytest` and `uv run pytest` both failed to spawn pytest).

## Findings

1. **blocker — `packages/exeboard-ai/src/exeboard_ai/document_intelligence/ir/models.py:356-366`, `427-455`, `662-681` — malformed span/page IDs can become citeable evidence.**
   - Why it matters architecturally: `SpanId = str` and `PageId = str` are not validated by type aliases. `DocumentIR` validates duplicate span IDs and content offsets, and layout citation validation only checks that a referenced span exists plus `startswith(document_id)`. A span ID with the right document prefix but malformed shape or embedded wrong page can pass and later be cited as exact evidence. This breaks the core evidence-backed invariant that citations are machine-resolvable, page-specific source spans, not arbitrary strings.
   - Exact minimal fix: in `DocumentIR._validate_document_structure`, validate `page.page_id == make_page_id(self.document_id, page.page_number)` and validate every `TextSpan.span_id` against the canonical span-id format, including embedded `document_id` and embedded page number matching `span.page_number`. Add tests for malformed span IDs, wrong-document page IDs, and span IDs whose embedded page disagrees with `TextSpan.page_number`.

2. **high — `packages/exeboard-ai/src/exeboard_ai/document_intelligence/ir/models.py:95-117`, `540-560`, `652-660` — layout bounding boxes are not fully trustworthy provenance.**
   - Why it matters architecturally: `BoundingBox` accepts negative coordinates, non-finite floats, and extra fields by default, while `DocumentIR` only checks that `BoundingRegion.page_number` exists. For evidence-backed UI highlighting and future Docling/cloud adapter parity, page/bbox provenance must be normalized and valid for the page, not merely present.
   - Exact minimal fix: set `BoundingBox.model_config = ConfigDict(frozen=True, extra="forbid")`; require finite coordinates and non-negative `x0/y0/x1/y1`; and when a `Page.width`/`height` is available, validate every layout `BoundingRegion.bbox` lies within that page’s dimensions for `pdf_points_top_left`. Add tests for negative, infinite/NaN, out-of-page, and extra vendor-coordinate fields.

3. **high — `packages/exeboard-ai/src/exeboard_ai/document_intelligence/ir/models.py:174-181`, `499-510`, `597-624`, `627-649` — table/figure wrapper blocks can exist without required detail objects.**
   - Why it matters architecturally: a `LayoutBlock(block_type="table")` may omit `table_id`, and a `LayoutBlock(block_type="figure")` may omit `figure_id`; such blocks can pass `DocumentIR` validation with no `Table` cells or `Figure` region. That lets the IR claim layout awareness while silently dropping the table/figure semantics needed for faithful summarization.
   - Exact minimal fix: in `LayoutBlock._validate_block_semantics`, require `table_id` when `block_type == TABLE` and require `figure_id` when `block_type == FIGURE`; keep the existing prohibition on those IDs for other block types. In `DocumentIR._validate_layout`, continue requiring those IDs to resolve to matching detail objects. Add tests for table/figure blocks with missing IDs and blocks whose IDs do not resolve to details.

4. **high — `packages/exeboard-ai/src/exeboard_ai/document_intelligence/ir/models.py:185-195`, `251-270`, `273-311` — cell and figure provenance can be structurally empty or caption-only.**
   - Why it matters architecturally: `TableCell` permits a content cell with neither `source_span_ids` nor `bounding_regions`, and `Figure` permits a figure with only caption/source spans and no visual bounding region. Empty cells should be omitted from a sparse table or carry a bbox if intentionally represented; figure captions must not substitute for figure-region provenance. Otherwise later claims can cite surrounding text while the table/figure location that gives the claim meaning is not auditable.
   - Exact minimal fix: add a `TableCell` model validator requiring at least one of `source_span_ids` or `bounding_regions`; represent truly blank cells only when a bbox is available. Require `Figure.bounding_regions` to be non-empty for `Figure` objects; caption-only evidence should remain a caption block until the visual region is known. Add tests for empty table cells and caption-only figures.

5. **medium — `packages/exeboard-ai/src/exeboard_ai/document_intelligence/ir/models.py:339-346`, `356-366`, `427-455` — parser-run lineage is not validated for spans.**
   - Why it matters architecturally: `DocumentLayout.parser_run_id` must resolve to an existing `ParserRun`, but `TextSpan.parser_run_id` can point to a missing run. That weakens audit lineage exactly where future layout/span alignment needs to prove which parser produced each citeable span.
   - Exact minimal fix: while collecting spans in `DocumentIR._validate_document_structure`, if `span.parser_run_id is not None`, require it to be in `parser_run_ids`. Add tests for valid span run IDs and missing span run IDs.

6. **medium — `packages/exeboard-ai/src/exeboard_ai/document_intelligence/ir/models.py:70-117`, `339-413` — schema boundaries still silently ignore non-layout extra fields.**
   - Why it matters architecturally: the new layout detail models use `extra="forbid"`, but `DocumentSource`, `BoundingBox`, `ParserRun`, `TextSpan`, `Page`, and `DocumentIR` do not. A future adapter can accidentally pass parser-native/vendor fields at the IR boundary and Pydantic will silently ignore them instead of failing fast, which hides adapter bugs and weakens the no-vendor-leakage contract.
   - Exact minimal fix: add `extra="forbid"` to all IR models, or at minimum to `BoundingBox`, `ParserRun`, `TextSpan`, `Page`, and `DocumentIR` before adding Docling. Add regression tests that extra Docling/native parser fields are rejected, not silently dropped.

7. **medium — `packages/exeboard-ai/src/exeboard_ai/document_intelligence/parsing/adapters/pymupdf.py:31-40`, `91-105`; `tests/integration/document_intelligence/test_pymupdf_parser.py:170-181` — missing/unreadable files can bypass parser-port exceptions.**
   - Why it matters architecturally: `parse()` calls `_make_document_source(path)` and `path.read_bytes()` before `_open_pdf()`. A missing file or filesystem read error will raise a raw `FileNotFoundError`/`OSError`, not `UnreadableDocumentError`, so parser-strategy orchestration cannot reliably distinguish unreadable documents from programmer errors.
   - Exact minimal fix: either open the PDF before hashing or wrap `path.read_bytes()` failures in `UnreadableDocumentError`. Add an integration test for a missing path and, if practical, an unreadable path.

8. **low — `packages/exeboard-ai/src/exeboard_ai/document_intelligence/ir/models.py:339-346`, `375-413` — frozen models still expose mutable lists.**
   - Why it matters architecturally: `ParserRun.warnings`, `Page.spans`, `DocumentIR.parser_runs`, and `DocumentIR.pages` are mutable lists inside frozen Pydantic models. Callers can mutate a validated IR after construction and invalidate provenance or parser lineage without revalidation. This is not the largest blocker because layout collections are tuples, but it is a regression risk for an evidence substrate intended to be immutable.
   - Exact minimal fix: convert these fields to tuples in a compatibility-safe migration, or add explicit copy/serialization boundaries and tests proving post-construction mutation cannot invalidate stored IR before downstream validation/chunking.
