- Note (Severity: High): `TableCell` can be accepted with neither citeable spans nor bounding-region provenance. The model defaults both to empty (`models.py:193-194`) and only validates roles/source-span tuple shape (`models.py:197-216`); `Table._validate_cells` checks bounds/overlap but not provenance (`models.py:251-270`). I verified a `DocumentIR` with a table cell `TableCell(row_index=0, column_index=0)` and no `source_span_ids`/`bounding_regions` validates successfully. This is a provenance gap against the plan's requirement that table cells preserve source spans and bounding regions (`pdf-parsing-strategy.md:347-349`, `403`) and the memory guard that visual-only objects use explicit page/bounding-region provenance. Impact: a layout-aware adapter could emit table cells that have row/column semantics but cannot be cited, highlighted, or audited back to page regions.
- Note (Severity: Medium): `LayoutBlock` allows `block_type="table"` or `block_type="figure"` with no `table_id`/`figure_id`, no detailed `Table`/`Figure`, and no bounding regions (`models.py:128-142`, `174-182`; `DocumentIR` only checks references when the IDs are non-`None` at `models.py:507-510`). I verified such table/figure blocks validate. This can make a layout claim table/figure structure while omitting the detailed table cells or figure provenance that the plan expects (`pdf-parsing-strategy.md:340-351`, `401-405`). If intentional as a lossy parser output, it should be explicitly documented/tested; otherwise require table/figure blocks to link to detail objects or carry enough provenance/failure signaling.
- Note (Severity: Low): `heading_level` is not constrained to heading/title-like blocks. The field is available on every `LayoutBlock` (`models.py:139`) and `_validate_block_semantics` only constrains table/figure IDs and text-bearing spans (`models.py:174-182`). A paragraph/table/footer can therefore carry `heading_level`, which may confuse future hierarchy consumers. Add validation or a test if heading levels are intended only for headings.
- Note (Severity: Low): The parser-port plan's broader test guard includes explicit no-layout, OCR-required, unsupported-document, and span-alignment failures (`pdf-parsing-strategy.md:355`). Current ports cover encrypted/unreadable/no-text plus layout extraction/span alignment (`ports.py:7-28`), but there is no dedicated OCR-required or unsupported-document type. This may be acceptable for this step if those are represented by `LayoutExtractionError`/messages, but the contract is less explicit than the guard.
